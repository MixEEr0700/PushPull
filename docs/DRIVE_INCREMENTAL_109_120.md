## Protocol and transport

Versioned manifests carry parent file/digest, generation and SHA-256 of reconstructed object map. Stable JSON-encoded paths partition object properties and ordered array records; corrections and deletions create changed references and explicit tombstones. Equal changed values share SHA-addressed objects. Every packet, object, generation, parent and reconstructed model is checked before existing canonical semantic validation and PPC1 encoding. Order is reconstructed via explicit array lengths/keys, not dates. Google-created timestamps label explicit recovery choices; devices maintain independent local lineages instead of selecting a winning remote head.

First upload is full; after 32 deltas, or before the cumulative chain budget would be exceeded, create a new independent full base. Keep earlier bases and deltas. No retention/deletion policy is enabled. Limits: 128 MiB cumulative UTF-8 chain, 50,000 partition rows, 64 levels and 32 deltas. Network bodies stream with a 128 MiB cap; workers terminate after 120 seconds. Catalog stops at 50,000 files. Limits refuse work rather than truncating data. JSON manifests are not gzip-compressed; local manual PPC1 remains the existing single compressed complete file.

POST uses a Google-generated file ID durably stored with the exact pending packet before upload. Retry GETs that same ID; uncertain POST/409 is followed by exact readback. Full chain validation and a reconstructed canonical PPC1 must succeed before the checkpoint and verified status are saved. Old checkpoints remain valid if POST or local checkpoint CAS fails. No best-effort POST success is reported as verification.

Heavy capture/encoding, partitioning, JSON parsing, hashing, semantic validation and chain reconstruction execute in workers. The existing transport keeps OAuth tokens on the main thread; a bounded worker RPC bridges read/create operations. Pending packets are persisted in the existing Drive metadata record under account scope with existing token CAS and operation serialization. No schema upgrade.

## Queue and UI

A successful native v2 finish writes a small backup-intent token in its existing strict transaction, with readback. The network is never awaited by finishing UI. A later Drive metadata CAS serializes the immutable pending packet; legacy queues are retained and never executed. Duplicate queue/send calls reserve one in-flight request synchronously. Offline/auth failure retains intent; startup/online/login resumes it. Transient authenticated failures retry with bounded backoff while the app runs. OAuth is invoked only by the user's connect gesture; tokens stay in memory. There is no promise of sending while PWA is closed.

After explicit account connection automatic PPC1 is enabled by default unless previously disabled. The advanced Drive section has its toggle and explicit send/retry; the restore flow lists PPC1 recovery points alongside existing legacy restore. Selection reconstructs a complete file then uses existing worker preview, separate confirmation, CAS, pending gate, native readback and strict complete. Automatic upload never restores remote data.

**Restore remains limited to a clean training profile.** A configured/connected Google client is permitted only for a point selected through the Drive flow, with no queued/pending uploads. Target defaults, journal and other auxiliary clean checks remain. Logical data is exact; physical epoch/CAS/device/account authority is regenerated by existing restore. Accounts/tokens/outboxes are not activated from the source. A failed claimed restore retains the existing fail-closed gate; retry in another clean profile. No in-place replacement of a used training profile.

## Limits

No real Google account/OAuth consent/Drive upload or Pixel 9 acceptance performed. No multi-year large-chain/p95/peak-heap or hardware power-loss measurement. Full canonical capture and verification still read the whole logical model locally; only changed objects go over upload. Reads of prior chains are needed to validate parents; this does not claim constant-time or constant-memory backup. Browser storage/Google quotas can refuse a pending packet. Retention is deliberately absent pending approval; storage grows and the catalog cap eventually refuses listing. Pending multi-store restore retains existing clean-profile/fail-closed limitations. Settings included are the existing canonical preferences and portable client ID, not physical Drive account authority. No legacy technical rescue archives are added to canonical data, per #123.
